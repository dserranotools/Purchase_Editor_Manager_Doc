## 1. Fundamental Concepts

### What problem does PEM solve?

The **SO99+** planning system generates automatic purchase proposals based on demand forecasts. However, these proposals do not take into account:

- **Actual surplus stock** in other warehouses that could be used instead of purchasing
- **Equivalent or substitute products** that could replace the proposed product
- **Minimum purchase/logistics** requirements imposed by suppliers
- **Customer-specific business rules** on which products can be exchanged
- **Order centralization** to optimize costs

**PEM** takes the proposals from SO99, enriches them with master data from the ERP, applies configurable business rules, and produces optimized purchase and transfer orders ready to be sent to the ERP.

### High-level business flow

```
SO99 generates proposals → PEM imports → PEM calculates (nets, substitutes, centralizes)
→ Planner reviews problems → Planner approves → PEM exports to ERP
```

## 2. Business Data Hierarchy

PEM organizes proposals into a 4-level hierarchy that reflects the purchasing organizational structure:

```
Plangroup (Planning Group)
│   Groups products that are reviewed with the same frequency
│   E.g.: "DAIRY - DAILY", "FROZEN - WEEKLY"
│
└── Supplier
    │   Groups all proposals from a single supplier
    │   E.g.: "DANONE", "NESTLÉ"
    │
    └── Warehouse
        │   Groups proposals for a single destination warehouse
        │   E.g.: "VAL4" (Valencia), "MAD1" (Madrid)
        │
        └── Proposal
            Specific product with quantity, date, cost
            Each proposal has an IdxProp:
            • Idx=0: Main proposal
            • Idx=1: Alternative 1
            • Idx=2: Alternative 2
```

### What is a Plangroup?

A **Plangroup** (planning group) defines:
- **Planning frequency**: how often it is reviewed (daily, weekly, etc.)
- **Centralization type**: ACCUM (centralizes) or NO_ACCUM (does not centralize)
- **Centralization level**: REG (via regional) or CEN (direct to central)

Example: The Plangroup "DAIRY_DAILY" is planned every day, centralized via regional (REG).

## 3. Proposal Processing

### Full Calculation Flow

```
┌──────────────────────────────────────────────────────────────┐
│ PHASE 1: TransferOrders SO99                                 │
│ • PEM imports TransferOrders generated by SO99               │
│ • Links each TransferOrder with its purchase proposal        │
│ • Netting: deducts the transferred quantity from the purchase│
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 2: Local Substitutions (same warehouse)                │
│ • For each proposal with pending quantity > 0:               │
│   a) Search for substitutes (S) in the same warehouse        │
│      → Obsolete items that can replace the order             │
│   b) Search for equivalents (D) in the same warehouse        │
│      → Different but interchangeable items                   │
│ • Validate against compensation rules                        │
│ • Netting: deduct found stock from the proposal              │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 3: Network Substitutions (entire logistics network)    │
│ • For each proposal with pending quantity > 0:               │
│   a) Search for substitutes (S) in the ENTIRE logistics net  │
│   b) Search for EQUAL (I) in the ENTIRE network              │
│      → Same product in another warehouse with overstock      │
│   c) Search for equivalents (D) in the ENTIRE network        │
│ • Validate against compensation rules                        │
│ • Netting                                                    │
│ • Generate TransferOrders for transfers between warehouses   │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 4: Delivery Minimums                                   │
│ • Evaluate each proposal against:                            │
│   - Minimum movement lot (MANP3)                             │
│   - Supplier minimum purchase (MANP4)                        │
│   - Minimum shipping costs (MANP5)                           │
│ • Mark non-compliant proposals for manual review             │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 5: Centralization                                      │
│ • For ACCUM-type suppliers:                                  │
│   - Group all proposals at the regional warehouse            │
│   - Generate TransferOrders from regional to each destination│
│ • For NO_ACCUM-type suppliers:                               │
│   - Keep proposals at their original warehouses              │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 6: Promotions and Discounts                            │
│ • Apply current supplier promotions                          │
│ • Adjust costs based on rebates and discounts                │
└──────────────────────────────────────────────────────────────┘
```

## 4. Quantity Netting

### What is netting?

**Netting** is the process of reducing the purchase quantity of a proposal using the available stock of substitute, equal, or equivalent products in other warehouses.

### Algorithm

```
For a proposal with QtyFinal = 100 units:

1. Search for candidates (substitutes/equivalents with stock)
2. Sort candidates by HIGHEST available equivalent stock
3. For each candidate, in order:

   Candidate A: 60 units in stock → EquivalentStock = 60
   QtyFinal (100) >= EquivalentStock (60)?
   → Yes → candidate.EquivalentStockUsed = 60
           QtyFinal = 100 - 60 = 40

   Candidate B: 50 units in stock → EquivalentStock = 50
   QtyFinal (40) >= EquivalentStock (50)?
   → No → candidate.EquivalentStockUsed = 40
           QtyFinal = 40 - 40 = 0

4. Result: QtyFinal = 0 (fully compensated)
   • 0 units are purchased
   • A TransferOrder of 60 units is generated from warehouse A
   • A TransferOrder of 40 units is generated from warehouse B
```

### What stock is used?

Depends on the compensation rule applied:

| Stock Type | Meaning | When used |
|---|---|---|
| **TotalStock** | All virtual stock of the warehouse | When the rule allows using all stock |
| **OverStock** | Only the stock exceeding projected demand | When the rule is conservative (only "surplus" stock) |

OverStock is calculated as: `min(OverStkQty_AvedemQty, OverStkQty_Projected)`

Additionally, the system verifies that the projected stock (future, within the leadTime) is above the MaxOutflow (maximum expected demand), to ensure the source warehouse is not being depleted.

## 5. Substitution and Compensation System

### 5.1 Three Types of Equivalence

| Type | Code | Meaning | Data source | Example |
|---|---|---|---|---|
| **Substitute** | **S** | Obsolete product replaced by a new one | `IN_ITEM_SUPERSSESIONS` (SO99) | Item "123" (discontinued) → Item "456" (new) |
| **Equal** | **I** | The SAME product in another warehouse | `ItemLocationList` (stock in other warehouses) | Item "789" in VAL4 → Item "789" in MAD1 |
| **Equivalent** | **D** | DIFFERENT product but functionally interchangeable | `IN_ITEM_EQUIVALENCES` (ERP) | Milk Brand A → Milk Brand B |

### 5.2 Search Order

The system searches for candidates in this order, moving to the next type only if the proposal still has pending quantity:

```
LOCAL (same warehouse):
  1st Substitutes (S) → QtyFinal > 0?
  2nd Equivalents (D) → QtyFinal > 0?

NETWORK (entire logistics network):
  3rd Substitutes (S) → QtyFinal > 0?
  4th Equals (I) → QtyFinal > 0?
  5th Equivalents (D) → End
```

**Note:** Equals (I) are only searched in Network, not in Local (it makes no sense to transfer the same product within the same warehouse).

### 5.3 Candidate Eligibility

A candidate is eligible if it meets ALL of these conditions:

1. **Sufficient stock**: `stockTotal > 0`
2. **Minimum lot**: `stockTotal >= minResLot` (stock must cover at least the minimum transfer lot)
3. **Valid warehouse level**: The level (N0, N1, N2, N3) is not `NoLevel`
4. **Compensation rule validation**: At least one rule allows the operation
5. **Sufficient equivalent stock**: `EquivalentStock >= minResLot` (after applying Total/OverStock)

## 6. Logistics Networks

### 6.1 Hierarchical Structure

Each product belongs to a **logistics network** that defines the warehouse hierarchy:

```
Central (CEN)
  │
  ├── Regional "EAST" (REG)
  │   ├── VAL4 (Valencia)
  │   ├── ALI1 (Alicante)
  │   └── CAS1 (Castellón)
  │
  ├── Regional "CENTER" (REG)
  │   ├── MAD1 (Madrid)
  │   └── TOL1 (Toledo)
  │
  └── Regional "SOUTH" (REG)
      ├── SEV1 (Seville)
      └── MAL1 (Málaga)
```

Logistics network data comes from `IN_RED_LOG` (imported from ERP).

### 6.2 Levels between Warehouses

When evaluating whether a product can move from warehouse A to warehouse B, the **level** is determined:

| Level | Meaning | Example |
|---|---|---|
| **N0** | Same warehouse | VAL4 → VAL4 |
| **N1** | Same region | VAL4 → ALI1 (both in EAST regional) |
| **N2** | Different region (regional destination) | MAD1 → VAL4 (different regionals) |
| **N3** | Remaining warehouses | MAD1 → ALI1 (non-regional warehouse from another region) |
| **NoLevel** | No relationship | Do not share a logistics network |

### 6.3 ScopeDistribution

Each product has a scope that limits how far it can be moved:

| ScopeDistribution | Meaning | Can use N2? | Can use N3? |
|---|---|---|---|
| `_ALL` | Can use any warehouse | ✅ Yes | ✅ Yes |
| `_ALL_R` | Can use regionals + rest | ✅ Yes (if dest is regional) | ✅ Yes (if dest is not regional) |
| `_REG` | Only its own region | ❌ No | ❌ No |

Comes from the `FREEATTR6` field in the MasterFile (imported from SO99).

## 7. Centralization by Lots and by Purchase

### 7.1 Why centralize?

Many suppliers require:
- **Minimum order** per warehouse (e.g.: minimum 100 units)
- **No split orders**: they deliver everything to a single warehouse

If one warehouse needs 30 units and another 40, separately they don't reach the minimum. **Centralizing** (30+40=70, closer to the minimum), you can negotiate better or at least meet restrictions.

### 7.2 Types of Centralization

| Type | Behavior |
|---|---|
| **ACCUM** | The supplier does NOT split orders. Everything is delivered to the regional/central warehouse. PEM automatically generates TransferOrders from the regional to each destination warehouse |
| **NO_ACCUM** | The supplier DOES accept split orders by warehouse. Not centralized |
| **ALL_WHOUSE** | The supplier delivers directly to each warehouse. No restrictions |

### 7.3 Centralization Levels

| Level | Route |
|---|---|
| **REG** | Supplier → Regional → (TransferOrder) → Destination warehouse |
| **CEN** | Supplier → Central → (TransferOrder) → Regional → (TransferOrder) → Destination warehouse |

### 7.4 Example

```
Supplier DANONE, Plangroup DAIRY, type ACCUM, level REG:

Without centralization:         Centralized:
VAL4: 30 units (doesn't reach)  REG_EAST: 110 units (reaches the minimum of 100!)
ALI1: 40 units (doesn't reach)  → TransferOrder REG_EAST→VAL4: 30 units
CAS1: 40 units (doesn't reach)  → TransferOrder REG_EAST→ALI1: 40 units
                                → TransferOrder REG_EAST→CAS1: 40 units
```

## 8. Need States: MANP3, MANP4, MANP5

### 8.1 State Table

| State | Code | Color | Business meaning |
|---|---|---|---|
| **NO_PROCESSED** | 0 | ⬜ Gray | Pending calculation |
| **MANP3** | 30 | 🔴 Red | **Missing minimum movement lot** |
| **MANP3_V** | 31 | 🔴 | MANP3 reviewed by the planner |
| **MANP4** | 41 | 🟠 Orange | **Missing supplier minimum purchase** |
| **MANP4_V** | 42 | 🟠 | MANP4 reviewed by the planner |
| **MANP5** | 51 | 🟡 Yellow | **Missing minimum shipping costs** |
| **MANP5_V** | 52 | 🟡 | MANP5 reviewed |
| **MANP5_C** | 53 | 🟡 | Centralized (managed at the central) |
| **TO_EXPORT** | 90 | 🔵 Blue | Approved, ready to export to ERP |
| **EXPORTED** | 95 | 🟢 Green | Already exported to ERP |
| **NOT_NEEDED** | 0 | ⬜ Gray | Not needed (quantity = 0) |
| **PROCESSED** | 100 | ⬜ | Already processed (no changes) |

### 8.2 MANP3 — Minimum Movement Lot

**Problem:** The net quantity does not reach the **minimum movement lot** required for purchase or transfer of that item at that location.

**Cause:** Restriction in `IN_SUPP_ITEM_MOV` (minimum batch, increment, safety stock per supplier+item).

**What the planner sees:**
- Product, warehouse, required quantity (e.g.: 15 units)
- Required minimum lot (e.g.: 50 units)
- Action options:
  - **BUY**: Force purchase of 50 units (assumes cost overrun)
  - **NO_BUY**: Do not buy (assumes stockout risk)
  - **TRANSFER**: Search for transfer from another warehouse

### 8.3 MANP4 — Supplier Minimum Purchase

**Problem:** The net quantity does not reach the **minimum purchase** required by the supplier for that location.

**Cause:** Restriction in `IN_SUPP_LOCATION_COMPRA` (minimum order per supplier+location).

**What the planner sees:**
- Required quantity vs supplier minimum
- Options:
  - **BUY**: Force purchase of the minimum
  - **NO_BUY**: Do not buy
  - **CEN_NO_BUY**: Centralize (group with other warehouses) to reach the minimum

### 8.4 MANP5 — Minimum Shipping Costs

**Problem:** The quantity does not reach the **minimum shipping costs** (delivery charges).

**Cause:** Restriction in `IN_SUPP_LOCATION_PORTES`.

**What the planner sees:**
- Similar to MANP4 but related to transportation costs
- Options:
  - **BUY**: Assume the shipping costs
  - **NO_BUY**: Do not buy
  - **CEN_NO_BUY**: Centralize to share shipping costs

### 8.5 Planner Actions (Restriction_Action)

| Action | Meaning | Effect |
|---|---|---|
| **ADVANCE** (0) | Advance | Move quantity to a future period (consolidate) |
| **BUY** (1) | Buy | Force the purchase ignoring the restriction |
| **NO_BUY** (2) | Do not buy | Eliminate the need |
| **TRANSFER** (3) | Transfer | Cover with stock from another warehouse |
| **CEN_NO_BUY** (4) | Centralize without buying | Group at central to reach the minimum |

## 9. Compensation Rules (RuleEquivalences)

### 9.1 What is a Compensation Rule?

A compensation rule defines **under what conditions** a product (source) can be used to cover the need of another product (destination).

Rules are configured in the `IN_RULE_EQUIVALENCES` table (imported from ERP) and are editable from PEM via `RuleCompensaDialog`.

### 9.2 Structure of a Rule

| Field | Question it answers | Example |
|---|---|---|
| `whouse_use` | Same warehouse (1) or different (2)? | 2 (between warehouses) |
| `typeEquiv` | Substitute (S), Equal (I) or Equivalent (D)? | D |
| `whouseOri` | From which warehouse can stock be given up? | "ALL" (any) |
| `whouseDest` | To which warehouse can it be sent? | "VAL4" (only to Valencia) |
| `aplicationType` | At what product level does it apply? | FAMI (family) |
| `aplicationCode` | What specific code? | "DAIRY" |
| `class_ABC_gen` | What general ABC classification? | "A" (only top products) |
| `class_ABC_SKU` | What SKU ABC classification? | "" (no restriction) |
| `expensive` | Expensive (S), cheap (N) or all (ALL) products? | "ALL" |
| `travel` | Can the product travel between warehouses? | "S" (yes) |
| `TotalStock` | Use all stock (true) or only OverStock (false)? | false (only overstock) |

### 9.3 Rule Example

```
Rule "COMP_DAIRY_REG":
  whouse_use = 2 (between warehouses)
  typeEquiv = D (equivalents)
  whouseOri = ALL
  whouseDest = ALL
  aplicationType = FAMI
  aplicationCode = DAIRY
  class_ABC_gen = (empty)
  class_ABC_SKU = (empty)
  expensive = ALL
  travel = S
  TotalStock = false (only OverStock)

Meaning:
"Equivalent products (D) from the DAIRY family can be compensated
between any warehouse, using only overstock (not all stock),
as long as the product can travel."
```

### 9.4 Validation Algorithm

```
For a proposal and a candidate:

1. Filter ALL rules that:
   • Match on whouse_use (1=local, 2=network)
   • Match on typeEquiv (S, I, D)

2. For each rule, verify in cascade:
   ✅ Is the candidate's source warehouse allowed?
   ✅ Is the proposal's destination warehouse allowed?
   ✅ Does the product classification match? (section/line/family/brand...)
   ✅ Does the candidate's general ABC classification match?
   ✅ Does the SKU ABC classification match?
   ✅ Does the expensive/cheap restriction match?

3. From the matching rules, select THE MOST RESTRICTIVE
   (the one with the most specific filters filled in)

4. With the winning rule:
   • If local (whouseUse=1) → OK
   • If network (whouseUse=2) → verify the product "travels"
   • If TotalStock=true → OK
   • If TotalStock=false (OverStock) → verify real overstock exists:
     - OverStkQty_AvedemQty > 0
     - Projected stock > MaxOutflow in the leadTime
```

### 9.5 How is "restrictiveness" measured?

Each rule gets a score based on the filters it applies:

| Filter filled in | Points |
|---|---|
| `class_ABC_gen` not empty | +1 |
| `class_ABC_SKU` not empty | +2 |
| `aplicationCode` not empty | + aplicationType value (1 to 8) |
| `whouseDest` specific (not "ALL") | +4 |
| `whouseOri` specific (not "ALL") | +4 |

**Scoring example:**
- Rule A: `aplicationCode="DAIRY"` (FAMI=3), `whouseDest="VAL4"` (+4) → 7 points
- Rule B: `aplicationCode="DAIRY"` (FAMI=3) → 3 points
- **Rule A wins** for being more specific

## 10. Supplier Restrictions

### 10.1 Types of Restrictions

| Type | Table | Meaning |
|---|---|---|
| **Movement (MANP3)** | `IN_SUPP_ITEM_MOV` | Minimum lot, increment, safety stock per supplier+item |
| **Purchase (MANP4)** | `IN_SUPP_LOCATION_COMPRA` | Minimum order (value and units) per supplier+location |
| **Shipping (MANP5)** | `IN_SUPP_LOCATION_PORTES` | Minimum shipping costs per supplier+location |
| **Promotions** | `IN_SUPP_LOCATION_PROMOTIONS` | Discounts, rebates, bonuses |

### 10.2 Hierarchical Search

For minimum purchases, the system searches in this order:

```
1. Search for restriction for specific Supplier + Location
   E.g.: "DANONE_VAL4"
   
2. If it doesn't exist, search for restriction for Supplier + ALL
   E.g.: "DANONE_ALL" (applies to all supplier locations)

3. If it exists for Supplier+Location, select the best restriction
   that applies to the specific item (by segmentation, family, etc.)
```

## 11. Import Process

### What is imported and from where?

| Source | Data | Frequency |
|---|---|---|
| **SO99+** | Proposals, MasterFile, ItemLocations, Suppliers, Warehouses, SuperSessions, Plangroups | Every planning day |
| **ERP** | Equivalences, Segmentations, Deployment Stock, Rules, Logistics Network, Supplier Restrictions | On demand ("Load ERP Info") |

### Import Flow from SO99

```
1. Determine which Plangroups are due for planning today
   → Based on each Plangroup's planning frequency

2. Safety backup
   → Current proposals → BACK_IN_PROPOSALS1_DATE
   → Logs → BACK_LOGS

3. Cleanup of obsolete data
   → Already processed proposals (STATUS='P')
   → Old TransferOrders
   → Logs older than N days

4. Import master data
   → Products, locations, suppliers, warehouses

5. Import today's proposals
   → Only from Plangroups due today
   → Only unprocessed proposals

6. Import TransferOrders
   → Transfers between warehouses planned by SO99
```

## 12. Export Process

### What is exported?

| Table | Content | Destination |
|---|---|---|
| `OUT_PURCHASE_ORDERS` | Final purchase orders | ERP (INTER_SO99) |
| `OUT_TRANSFER_ORDERS` | Transfer orders between warehouses | ERP |
| `OUT_SUBSTITUTIONS` | Substitutions applied | ERP |

### Export Flow

```
1. Planner marks Plangroups as "To Export"
   → Proposals transition to TO_EXPORT state (90)

2. Planner clicks "Export"

3. PEM:
   a) Clears OUT_* tables (TRUNCATE)
   b) Inserts into OUT_PURCHASE_ORDERS:
      - Only proposals with QtyFinal > 0
      - Only proposals in TO_EXPORT state
      - Includes: item, description, quantity, cost, supplier, warehouse, date
   c) Inserts into OUT_TRANSFER_ORDERS:
      - TransferOrders generated by PEM
   d) Inserts into OUT_SUBSTITUTIONS:
      - Record of which stock was used to compensate each proposal

4. Executes export Stored Procedure
   → Moves data from OUT tables to equivalent tables in INTER_SO99

5. Proposals transition to EXPORTED state (95)

6. The ERP picks up data from INTER_SO99 and generates:
   - Actual purchase orders
   - Actual transfer orders
```

## 13. Business Glossary

| Term | Definition |
|---|---|
| **SO99+** | Demand planning system that generates automatic purchase proposals |
| **PEM** | Purchase Editor Manager — this application |
| **ERP** | Target enterprise management system (SAP, Navision, etc.) |
| **Plangroup** | Planning group: set of products reviewed with the same frequency |
| **Proposal** | Purchase suggestion for a product in a warehouse, generated by SO99 |
| **Netting** | Reducing the purchase quantity using available stock from other sources |
| **Substitute (S)** | Obsolete/discontinued product replaced by the proposal's product |
| **Equal (I)** | The same product in another warehouse with surplus stock |
| **Equivalent (D)** | Different but functionally interchangeable product |
| **Candidate** | Product+warehouse that has stock and could be used to compensate a proposal |
| **MANP3** | Need that does not reach the minimum movement lot |
| **MANP4** | Need that does not reach the supplier's minimum purchase |
| **MANP5** | Need that does not reach the minimum shipping costs |
| **Centralization** | Grouping orders from multiple warehouses into a higher-level one to meet minimums |
| **ACCUM** | Plangroup type that requires centralization (supplier does not split orders) |
| **Logistics Network** | Warehouse hierarchy: Central → Regional → Local |
| **TransferOrder** | Goods transfer order between two warehouses |
| **OverStock** | Stock exceeding projected demand — "surplus stock" available for transfer |
| **TotalStock** | All virtual stock of the warehouse, including that needed for own demand |
| **ScopeDistribution** | Geographic scope up to which a product can be distributed |
| **ABC** | Product classification by importance: A (top), B (medium), C (low) |
| **SKUL** | SKU + Location: composite identifier of product in a specific warehouse |
| **LeadTime** | Time it takes for an order to arrive after it is issued |
| **BulkInsert** | Mass data insertion using `SqlBulkCopy` for maximum performance |
